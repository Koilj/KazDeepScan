Ниже — практичный план, по которому проект можно реально довести до рабочего сервиса на вашем ПК. Главное решение: сначала делаем надёжный анализ загруженных файлов, затем поток/звонки и Telegram. Иначе интерфейсы появятся раньше, чем появится проверенная модель.


## 0. Зафиксировать границы MVP

Первая версия должна:

- принимать WAV, MP3, OGG, M4A;
    
- поддерживать русский, казахский и смешанную речь;
    
- выдавать `p_ai` — калиброванную вероятность синтеза;
    
- показывать сегменты записи с повышенным риском;
    
- возвращать статусы `likely_human`, `likely_ai`, `uncertain`;
    
- корректно отказываться от слишком короткой, тихой или повреждённой записи.
    

Не обещаем «истину»: результат — оценка риска. Для звонков сначала используем тот же движок скользящих окон, но не начинаем с интеграции в телефонию.

## 1. Подготовить окружение и репозиторий

Стек:

- Python 3.11;
    
- актуальный PyTorch с официальной сборкой CUDA 12.8+ — это важно для RTX 5060 Ti / `sm_120`;
    
- `transformers`, `torchaudio`, `ffmpeg`, `soundfile`;
    
- `FastAPI` для API;
    
- `DVC` для версий данных;
    
- MLflow или Weights & Biases для экспериментов;
    
- Docker для поставки;
    
- Gradio только как временный интерфейс проверки.
    

Структура проекта:

```text
kazdeepscan/
  configs/
  data/
    raw/
    processed/
    augment_cache/
  manifests/
  src/
    data/
    models/
    training/
    inference/
  api/
  tests/
  docs/
  models/
```

Сразу добавить:

- фиксированные версии зависимостей (`uv.lock` или `poetry.lock`);
    
- `.gitignore` для аудио, чекпоинтов и секретов;
    
- `pre-commit`, `ruff`, `pytest`;
    
- тест GPU: CUDA доступна, `bf16` работает, модель может сделать forward pass.
    

Готовность этапа: один скрипт читает аудио, приводит его к 16 кГц mono и успешно запускает модель на GPU.

## 2. Описать контракт данных и угрозы

В `docs/threat_model.md` зафиксировать, что детектируем:

- TTS: текст → синтетическая речь;
    
- voice conversion / клонирование голоса;
    
- синтез после сжатия мессенджером;
    
- replay: проигрывание синтезированной речи через динамик и повторная запись;
    
- аудио с шумом, эхом, комнатой, телефонией.
    

Не включать в обещания первой версии:

- точное определение конкретного генератора;
    
- идентификацию личности;
    
- гарантии на неизвестные будущие модели синтеза;
    
- юридическое заключение о мошенничестве.
    

Схема одной строки манифеста:

```json
{
  "id": "uuid",
  "path": "processed/...",
  "label": "bonafide",
  "language": "kk",
  "speaker_id": "hashed_id",
  "source_corpus": "ksc2",
  "generator_family": null,
  "channel": "android",
  "parent_id": "original_recording",
  "license_bucket": "production_candidate",
  "split": "train"
}
```

`parent_id` обязателен: все варианты одного файла, его кодеки и аугментации должны оказаться только в одном split.

## 3. Собрать данные без юридических и ML-утечек

Разделите хранилище и эксперименты на две корзины:

|Корзина|Что входит|Где использовать|
|---|---|---|
|`production_candidate`|Свои записи с согласием, Common Voice ru/kk, KSC2, KSC SLR102 — после проверки актуальных условий|Кандидат в коммерческое обучение|
|`research_only`|RuASD, MLAAD, отдельные TTS-веса с NC-лицензией, спорные корпуса|Исследование и внешний тест|

Не смешивать их «случайно» одним манифестом.

### Настоящая речь

Соберите стартовый набор:

- русский: минимум 5 часов;
    
- казахский: минимум 5 часов;
    
- по возможности code-switching;
    
- разные дикторы, пол, возрастные группы, темпы речи;
    
- студийный микрофон, Android, iPhone, мессенджеры, телефонная запись;
    
- тишина, офис, улица, автомобиль, комната с эхом.
    

Для каждого участника — письменное согласие: запись, обучение модели, срок хранения, возможность отзыва. Реальные банковские или личные голосовые без согласия не использовать.

### Синтетическая речь

Создайте собственный набор фейков из согласованных исходных голосов:

- легально проверенные русские и казахские голоса Piper;
    
- KazakhTTS2 для казахского;
    
- Silero только после проверки конкретной лицензии и поддержки языка;
    
- F5-TTS и XTTS — только как исследовательские источники, так как их веса могут быть non-commercial;
    
- несколько режимов: нейтральная речь, эмоции, быстрый темп, паузы, длинные фразы, числа, имена, банковские сценарии.
    

Для каждой синтетики хранить:

```text
generator + version + voice + prompt/text + sampling params +
source speaker consent + post-processing chain
```

Не обучаться на одной синтезирующей системе: модель быстро научится находить её артефакты и провалится на новом генераторе.

Готовность этапа: есть первый набор 20 часов — по 5 часов bona fide и spoof для каждого языка — с полностью заполненными манифестами.

## 4. Сделать единый аудио-конвейер

Для каждого файла:

1. Проверить MIME, размер, длительность и декодируемость через `ffprobe`.
    
2. Сохранить оригинал отдельно.
    
3. Привести рабочую копию к PCM WAV, mono, 16 кГц.
    
4. Проверить клиппинг, тишину, уровень сигнала, длительность речи.
    
5. Найти речь через VAD.
    
6. Разбить на окна по 4.04 секунды — это 64 600 сэмплов.
    
7. На обучении брать случайный crop, на инференсе — окна с шагом 2 секунды.
    

Короткие файлы дополнять отражением или нулями, но обязательно передавать в модель маску реальной длины.

---

## 5. Построить реалистичную аугментацию

Аугментация должна идти только в train и одинаково применяться к bona fide и spoof. Валидация и тесты — без случайных преобразований.

Используйте `RawBoost` как часть аугментации плюс собственный конвейер:

- шумы MUSAN и собственные шумы: SNR 5–30 dB;
    
- сложный режим: 0–5 dB, но редко;
    
- комнатные импульсные характеристики, эхо, реверберация;
    
- gain, clipping, low/high-pass, эквализация микрофона;
    
- ресемплинг 8/12/16/24/48 кГц;
    
- кодеки: Opus, AAC, MP3, G.711 A-law/u-law;
    
- имитация потерь пакетов: выпадения, короткие дубли, сглаживание;
    
- replay-цепочка: синтетика → динамик/комната → микрофон.
    

Не накладывать все искажения разом. На один пример — максимум две-три операции. Каждая операция и её random seed логируются.

Отдельно сделать фиксированные наборы тестов:

- `clean`;
    
- `messenger`;
    
- `telephony`;
    
- `noisy`;
    
- `replay`;
    
- `unseen_generator`.

## 6. Сделать baseline, прежде чем обучать большую модель

Первый baseline нужен не ради качества, а чтобы найти ошибки в данных.

Модель B0:

```text
waveform 16 kHz
→ XLS-R 300M encoder (заморожен)
→ attentive/statistics pooling
→ MLP classifier
→ spoof logit
```

Обучение:

- balanced sampler по классу, языку и источнику;
    
- 5–10 эпох только голова;
    
- `BCEWithLogitsLoss`;
    
- сохранять метрики отдельно для ru, kk, code-switching и каналов;
    
- не использовать test для настройки.
    

Готовность этапа:

- обучение воспроизводимо по одной команде;
    
- есть ROC-AUC, PR-AUC, EER и FPR/TPR;
    
- проверено, что один диктор не попал одновременно в train и test;
    
- модель не «угадывает» путь файла, источник или кодек вместо класса.
    

Этот baseline ещё нельзя показывать как продукт.

## 7. Обучить основную модель

Основной кандидат:

```text
64 600 аудиосэмплов
→ XLS-R-300M, все hidden states
→ обучаемая взвешенная сумма слоёв
→ attentive statistics pooling
→ классификатор bona fide / spoof
```

Почему: XLS-R обучен на множестве языков и лучше переносится на русский/казахский, чем англоязычные антиспуфинговые модели.

Обучение в две стадии на вашей RTX 5060 Ti 16 ГБ:

1. **Stage A** — encoder заморожен, batch 16–24, учим классификационную голову.
    
2. **Stage B** — разморозить последние 6–8 блоков XLS-R, включить `bf16`, gradient checkpointing, batch 4, gradient accumulation 8.
    
3. Сохранять лучший чекпоинт не по train loss, а по `EER` на dev с unseen generator/channel.
    
4. Сравнить с конкурентом: AASIST как waveform-модель.
    

Не выбирать архитектуру «по одной красивой метрике». Побеждает модель, которая лучше держится на:

- новом синтезаторе;
    
- новом дикторе;
    
- новом телефоне или мессенджере;
    
- русском и казахском по отдельности;
    
- коротких и длинных записях.

## 8. Правильно разделить train/dev/test

Минимальные правила:

- один диктор — только в одном split;
    
- один генератор или его конкретная версия — целиком в одном OOD-test, если проверяем переносимость;
    
- один исходный файл и все его кодированные копии — только в одном split;
    
- тексты желательно разделять, особенно для собственного TTS;
    
- финальный test открывать только после фиксации модели и температуры.
    

Обязательные отчёты:

|Срез|Что измерять|
|---|---|
|Язык|ru / kk / code-switching|
|Канал|clean / Android / iPhone / Telegram / phone|
|Атака|TTS / VC / replay|
|Генератор|seen / unseen|
|Длительность|<3 с, 3–10 с, >10 с|
|Уровень шума|clean / mild / hard|

## 9. Калибровать вероятность

Нельзя брать вероятность из `sigmoid` и называть её калиброванной.

Правильная схема:

1. Модель выдаёт logit для каждого 4-секундного окна.
    
2. Логиты агрегируются по записи.
    
3. На отдельном `dev`-наборе обучается temperature scaling.
    
4. Уже после калибровки получается `p_ai`.
    

Для длинной записи выводить два значения:

- `p_ai_global` — риск по всей записи;
    
- `p_ai_peak` — риск наиболее подозрительных сегментов.
    

Так вы не пропустите короткую синтетическую вставку в длинном настоящем звонке.

Проверять ECE и Brier score. Порог `likely_ai` выбирать по допустимому ложному срабатыванию, например по метрике `TPR@FPR=1%`, а не «на глаз».

## 10. Сделать API и интерфейс

Сначала FastAPI:

```http
POST /v1/analyze
```

Ответ:

```json
{
  "model_version": "v0.3.0",
  "language": "kk",
  "decision": "uncertain",
  "p_ai_global": 0.61,
  "p_ai_peak": 0.84,
  "duration_s": 27.4,
  "segments": [
    {"start_s": 8.0, "end_s": 12.0, "p_ai": 0.84}
  ],
  "quality_flags": ["telephone_codec"]
}
```

Параллельно сделать Gradio-интерфейс:

- drag-and-drop аудио;
    
- плеер;
    
- итоговая оценка;
    
- временная шкала подозрительных сегментов;
    
- предупреждение о короткой/некачественной записи.

## 11. Добавить потоковый режим и затем Telegram

Потоковый режим:

- принимать чанки по 1 секунде;
    
- держать буфер 4.04 секунды;
    
- запускать анализ каждые 2 секунды;
    
- сглаживать результат по нескольким окнам;
    
- не показывать вердикт до накопления достаточной речи.
    

Telegram-бот добавлять только после API:

- `aiogram 3`;
    
- скачивание голосовых сообщений по file ID;
    
- лимит длительности и размера;
    
- удаление временного файла сразу после анализа;
    
- не логировать аудио и токены;
    
- понятное сообщение: «оценка риска, не доказательство мошенничества».
    

Интеграцию с реальными звонками через Asterisk/FreeSWITCH оставляем последней: там потребуются отдельно согласие участников, законность перехвата и реальные тесты с телефонной сетью.

## 12. Безопасность, приватность и эксплуатация

До пилота внедрить:

- API-ключи, rate limit, ограничения форматов/размера/длительности;
    
- запрет передачи пути к файлу пользователем;
    
- автоматическое удаление загруженного аудио;
    
- логи только с ID запроса, длительностью, версией модели и техническими флагами;
    
- аудио для улучшения модели — только по отдельному opt-in;
    
- политика хранения и удаления;
    
- model card: назначение, данные, ограничения, известные ошибки;
    
- юридическая проверка работы с голосовыми и биометрическими данными в Казахстане.

## 13. Оптимизация и поставка

Не начинайте с ONNX. Сначала стабилизируйте PyTorch-инференс.

После этого:

1. Сравнить PyTorch и ONNX Runtime на одинаковых входах.
    
2. Проверить, что оценки не расходятся сверх установленного допуска.
    
3. Замерить latency, VRAM, RPS.
    
4. Упаковать сервис в Docker с NVIDIA runtime.
    
5. Добавить `/health` и `/model-info`.
    
6. Версионировать модель, калибратор, манифест данных и конфиг как единый релиз.
