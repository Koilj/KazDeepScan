## 5. Этап C — завершённый blind research suite

Этот historical research suite завершён. Его final errors не используются для выбора v3 или
последующих recipe; следующий новый suite потребует других, действительно unevaluated assets.

### 5.1. Требования к источникам

- новые exact assets, которые ни один checkpoint проекта ещё не оценивал;
- отдельные RU, KK и mixed роли, без pooled score;
- новый точный checkpoint/runtime route, отсутствующий во всех сохранённых manifests;
- architecture-component, family и speaker/voice alias overlaps раскрываются отдельно; из-за
  неполной RuASD metadata не заявлять недоказуемую absolute architecture novelty;
- bona-fide counterpart с максимально сильными правами и group provenance;
- text-only TTS со встроенными публичными voices; reference audio и cloning запрещены;
- exact revision, license, weights/artifact hashes, voice ID и generation parameters;
- acoustic review до inference, а не после него.

Готового публичного независимого RU binary source сейчас не найдено. ToneSpeak spoof-only и
не закрывает требование bona-fide counterpart. YO-CPT и Dusha эту роль также не выполняют.

### 5.2. Допустимый практический вариант

Если новый source-level binary release не появится, создать ограниченный research suite из:

- ранее не использованных FLEURS RU/KK bona-fide assets;
- ранее не использованных KSC2 mixed assets;
- нового, предварительно проверенного exact TTS route для каждой языковой роли;
- заранее утверждённых текстовых пар и двух независимых acoustic reviews.

Такой suite может быть asset-level blind, но без нового corpus и verified speaker IDs нельзя
объявлять его полностью source- или speaker-independent.

## 7. Этап E — API или product track, только по отдельному решению

Для локального research demo всё равно нужен отдельный release contract. Для product route
дополнительно обязательны:

- commercial-clean train/dev/calibration/test data;
- подтверждённые права на ML training, synthetic derivatives и deployment;
- verified speaker/voice groups и независимый binary OOD protocol;
- product calibration и пороги по заданной цене ошибок;
- model/data cards, latency, security, privacy и retention review;
- UX с abstention и без утверждений о личности или мошенничестве.

Только после этого можно реализовать scorer interface, загрузку versioned model release и
перевести `/readyz` из `503`. Streaming, Telegram и телефония идут после надёжного file mode, а
не раньше.

## 8. Рекомендуемый порядок после v3

1. Не повторять Stage-C, Stage-D или v3 run и не использовать их final errors для tuning.
2. Silero V5.5 RU/fixed `eugene` уже прошёл source/rights/route review, а 80-record immutable
   selection закреплён. Следом extract только этот metadata-audited Common Voice RU `test` slice,
   затем QA/VAD без backfill; не переиспользовать 55 Stage-D/v3 pairs как blind test.
3. Если нужен product/API route — остановиться до отдельного commercial-rights, privacy,
   verified-speaker, product-calibration и deployment contract.

Не начинать AASIST, новый full fine-tune или API score только ради повышения этой метрики: это не
исправит главный риск — отсутствие независимого, ещё не оценивавшегося final source.
